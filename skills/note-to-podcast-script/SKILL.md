# 笔记 → 播客脚本

## 什么时候用

用户给你一篇笔记/文档（或一段长文本），想要一份适合口语朗读、听起来像真人在聊天（而不是 AI 念稿）的播客脚本。默认双人对谈，用户明确要求"单人朗读/独白"时才切换成单人模式。

**这个 skill 不调用任何外部 LLM API** —— 执行它的你（不管是 Claude Code、龙虾、Hermes agent 还是 opencode）本身就是一个 LLM，直接照着下面几段指令，分阶段在自己的推理里完成"策划→编剧→质检"，把最终结果写成一个 JSON 文件即可。这样这个 skill 才能脱离任何特定的 LLM API 账号，被任何 agent 框架复用。

## 输入

- 一份或多份源文档（文本内容，可以是 markdown 笔记、文章等）
- 说话人配置：1~4 人。每人需要 `id`（脚本里用来引用，比如 `A`/`B`）、`name`（显示名）、`role`（人设描述，比如"资深工程师，说话直接、偶尔毒舌"）、`voice`（TTS 音色 id，交给下游 `text-to-speech-doubao` skill 用；如果用户没指定，先只填 id/name/role，音色留给下一步再补）
- 风格调性 `tone`：一段话描述整体语气，比如"自然口语化，像日常聊天一样有基本的语气词和停顿，不要用新闻联播式的播报腔朗读"（用户没给就用这句默认值）
- 可选的自定义补充要求 `customInstructions`（优先级高于下面的通用规则）

人数为 1 时是**单人朗读模式**，2~4 人时是**多人对谈模式**，两种模式共用同一套规则，只在下面标注的几处措辞不同。

## 第一阶段：策划大纲（Planner）

**目标**：不写台词，先想清楚这期播客的叙事结构。

在心里（或草稿里）按下面的规则给自己下达指令，然后产出一份大纲：

1. 先想清楚目标听众是谁（比如"对这个领域有基础但不了解具体细节的听众"），这决定后面详略怎么拿捏。
2. 想好开场 Hook：一两句话，要在大约10秒音频内点题，并带出一个悬念/冲突/反常识的钩子，不能是"大家好欢迎收听"这种慢热套路。
3. 把内容拆成 3～5 个分段，每段要有明确主题、核心要点，以及这段内部可以借力的反差/冲突/追问角度——不是简单复述原文小标题，而是重新组织出"这段要怎么讲才抓人"。
4. 分段之间要有递进关系，由浅入深，不是信息平铺；宁可少几个分段、每段讲透，也不要为了"全面"堆砌成流水账。
5. 跳过或简化代码块、表格等不适合口语转述的内容，只保留核心逻辑和结论。
6. **（仅多人模式）** 规划分段时可以考虑哪段更适合让哪个角色主导、哪段该由另一位追问，但不用写进大纲，交给下一步写台词时自己发挥。

大纲产出结构（内部使用，不需要真的写文件，除非用户要求保留中间产物）：

```json
{
  "audience": "一句话describe目标听众",
  "hook": "开场要用的悬念/冲突/反常识钩子，一两句话",
  "segments": [
    {"topic": "这段讲什么，一句话概括", "keyPoints": "这段要讲到的核心要点", "conflict": "这段可以借力的反差/冲突/追问角度"}
  ]
}
```

## 第二阶段：写台词（Writer）

**目标**：把大纲展开成实际台词，这是核心产出。照着大纲的结构和节奏来写，但大纲只是骨架，具体怎么落成生动对话由你决定，整体走向、分段顺序、每段要制造的反差/冲突点不要偏离大纲。

写作规则（单人/多人共用，标注处除外）：

1. 开场要在最开始几句话（约10秒音频）就点明这期在聊什么，并带出悬念/冲突/反常识钩子，不要用"大家好欢迎收听"这种慢热套路。
2. 由浅入深，不是信息堆砌：宁可少讲几个知识点，也要保证听众能跟上、有收获，不要把原文所有细节都塞进去。
3. 围绕一个核心反差/冲突展开（比如"听众以为的常识 vs 实际发生的反常现象"），不要按时间顺序流水账式复盘。
4. 跳过或简化代码块、表格等不适合口语朗读的内容，只保留核心逻辑和结论，可以用类比/打比方代替技术细节。
5. **单人模式**：独白要有语气起伏和自我追问、自我转折，不是平铺直叙念稿。
   **多人模式**：说话人之间要有真实互动感：追问、打断、恍然大悟、自嘲，每个人都要按自己的人设说话，不是轮流念稿。
6. 台词长度要有节奏感，不是一刀切的短句：大部分常规来回控制在 20～70 个汉字左右，靠密集短句制造对话感；但讲一个具体案例、揭晓一个反转结论、或第一次深入解释一个核心概念时，可以也应该让一个人连续说一段更长的话（150～250 个汉字），这种"关键时刻的长镜头"正是播客区别于碎片问答的地方，不用怕超字数硬拆断。但这种长段落一期里只该出现在真正重点处，不能变成常态——如果发现连续好几轮都是长段落，就是走偏了，要拉回短促来回（**多人**追加：中途插入另一位说话人的追问、附和或打断；**单人**追加：靠自我追问、语气起伏制造节奏差，不是通篇一个语速讲完）。
7. 台词里可以适度用简短的自我修正、附和确认、中途卡壳增加真实感（"我换个说法""对对对""不完全是"），但具体用多密要服从"风格调性"设定，不要自己加码。
8. **情绪爆发点写法（已实测验证）**：真正决定 TTS 合成有没有情绪的，是这句话本身写得够不够短促。像"那你另请高明啊，你找我干嘛！"这种短促、口语化、带感叹号/省略号的句子，配上语气指令合成出来情绪很饱满；但一句话如果同时塞满技术解释、信息量很大，不管配什么语气指令，情绪都会被内容压掉。遇到惊讶、崩溃、恍然大悟、忍不住吐槽这类情绪节拍，可以在同一句台词里先用短促语气词开头（"啊？！""不是吧，"）再接具体内容，让整句保持短促有力；但**不要为了情绪饱满把同一个人紧挨着的一句情绪反应硬拆成两句独立台词**——已验证这样会导致两次独立合成的音频拼接处出现不自然断层，听感反而更差。只有另一位说话人接话/追问时才是独立的一句，同一个人一口气的情绪反应留在同一句台词里。
9. `tone` 字段不要写"震惊的语气""开心的语气"这种干巴巴的形容词标签——已验证写成场景化指令句效果明显更好，格式类似"你现在的状态是……，用……的方式说出这句话"，比如"你刚被对方的话惊到了，用又惊讶又想反驳的语气说这句话"。语气传达的情绪强弱、正式与否必须如实符合"风格调性"整体设定，不要自己加戏也不要比设定更收着演。
10. 语音合成一次只能执行一条整体语气指令，没法在一句话内部中途变调：如果台词本身包含明显的情绪/语气转折（"先自嘲叹气，然后变得认真自信"），必须拆成两条独立台词，各自配一个单一、精确对应的 `tone`，不要用复合描述硬塞给一整句话。

## 第三阶段：自我质检（Director，可选但推荐）

写完后，切换视角扮演"播客导演"，重新通读一遍脚本，检查：

1. 有没有明显 AI 套话/模板腔（"这是一个非常值得讨论的话题""没错，我完全同意""接下来让我们深入探讨一下"这类空洞场面话）。
2. **单人**：独白有没有语气起伏和自我追问、自我转折，而不是从头到尾一个语调平铺直叙；这是单人模式本来的样子，不要因为只有一个人在讲就判定不通过。
   **多人**：有没有连续好几句台词是同一个人大段独白、完全没有另一位追问/附和/打断（偶尔一两句"重点长镜头"允许，反复出现才算问题）。
3. 开场有没有在最开始几句话点明主题、带出钩子，而不是慢热铺垫。
4. 整体听感像不像真人在聊/讲、有没有自己的情绪起伏和思考过程，还是像照提纲念一遍。

只要不满足任何一条，回到第二阶段重写有问题的部分，再检查一遍，直到通过为止。不要把明显不合格的脚本直接交出去。

## 输出：script.json

最终把脚本写成如下结构，路径由调用方决定（比如 `./script.json`），这是下游 `text-to-speech-doubao` skill 的标准输入格式：

```json
{
  "mode": "dialogue",
  "speakers": {
    "A": {"name": "小林", "role": "资深工程师，说话直接、偶尔毒舌", "voice": "zh_male_dayi_uranus_bigtts"},
    "B": {"name": "阿May", "role": "刚入行一年的初级工程师，好奇心重、爱追问", "voice": "zh_female_xiaohe_uranus_bigtts"}
  },
  "segments": [
    {"speaker": "A", "text": "……", "tone": "……"},
    {"speaker": "B", "text": "……", "tone": null}
  ]
}
```

- `mode` 是 `dialogue`（多人）或 `monologue`（单人）。
- `speakers` 的 key 必须跟 `segments[].speaker` 精确对应，不要自己编造或改写。
- `voice` 字段如果用户没提供具体音色 id，先留空字符串，提示用户去 `text-to-speech-doubao` skill 里看音色列表再补上，不要瞎编一个不存在的音色 id。
- `text` 是要被 TTS 朗读的纯文本，**不要包含任何方括号描述、旁白说明或标点之外的标记**——语气用 `tone` 字段表达，不要塞进 `text` 里。

## 修订循环

用户看完脚本给反馈后，不要整篇推倒重来：

- 只是个别几句台词的措辞/语气问题 → 只重写那几句，前后台词保持不动，注意跟上下文衔接自然。
- 涉及整体结构、节奏、人设的问题 → 回到第二阶段，带着这轮反馈重新写，同时记得检查有没有不小心把用户之前提过、已经生效的历史反馈悄悄改回去。
- 用户追加了新的来源笔记 → 不管这轮反馈有没有明确提到这些新笔记，都必须在新脚本里找到它们跟本期播客主题相关的内容，实质性编排进去（新增一段对话，或让某句台词提到），不能只字不提当作没看见。

## 常见坑

- 不要把这个 skill 的三阶段理解成"必须调三次不同的 LLM API"——你自己一次会话内的多轮推理就够了，没有外部依赖。
- 不要因为要控制成本就跳过第三阶段自我质检；这一步不产生额外的外部 API 调用成本（不涉及 TTS），只是你自己多想一轮，值得做。
- 单人模式质检时最容易被误判成"不合格"（因为看起来只有一个人在唱独角戏）——参考上面第三阶段第2条，那是模式本身的正常形态。
